# Bounded recovered-opening supplement

- Source contract: `onejournal.recovered-opening-supplement.v1`
- Calculation output: `onejournal.recovered-opening-realized-preview.v1`
- Policy approval: owner `Yes proceed` after the explicitly bounded recovered
  evidence, copy-only financial rehearsal, commit and push proposal.
- Scope: at most two explicitly reviewed independent opening scopes. This is
  maintenance preparation, not a Phase 1 maturity or financial acceptance change.

## Evidence and identity

The authoritative parent is one exact, stored snapshot assembly v3 and its
validated active-history realized result. The supplement preserves recovered
retained JSON as a separate source kind. Original acquisition receipts and
capture instants remain unknown; a retained-file hash is not an original HTTP
response or verified acquisition-manifest claim.

Before normalization, the caller must verify every retained source-file checksum
and the same private broker account binding. The pure archive review compares
all retained versions against the parent's fills. Changed generated IDs, names,
normalized values, partial adapter exclusions, duplicate items and conflicts
with existing provider activities are withheld. No alias, preferred conflicting
version or replacement source-fill ID is permitted.

Admission requires an explicit source-ID and full instrument allowlist, one
supported security fill per activity, explicit opening effect, native currency,
UTC execution instant, quantity, price, multiplier where applicable, commissions
and fees. Both the source date and UTC execution date must precede the parent's
verified history window. Every retained raw/canonical-record pair must have
matching broker net cash and security-cost evidence. Exact cash movement must
reconcile to quantity, price, multiplier, commission and fees; missing, floating,
non-finite or conflicting evidence is not guessed.

Normalization observation time is recorded separately from the unknown original
capture instant. The calculation-only `NormalizedFill` uses this observation time
for its legacy metadata slot, consistent with the existing materialization's
assembly-observation convention. It is not persisted as evidence of a historical
provider fetch. Parent normalized records and acquisition metadata are unchanged.

## Financial calculation and limitations

The supplement binds its policy approval, exact parent assembly, realized
fingerprint, active revision identities, reviewed instruments, normalized rows,
every retained cash/source version and content fingerprint. Its loader requires
the exact expected fingerprint; there is no latest-file or latest-row selection.

The preview reads a quiescent disposable database only. It verifies stored parent
assembly bytes and the complete active-history realized authority before loading
the selected fills. Existing supported FIFO, lifecycle matching and ordinary
allocation identities are reused; tax-lot methodology, rounding, currency
conversion and old calculation fingerprints do not change.

Each selected chain must have no unmatched close or alias-dependent matching and
must reconcile its final quantity to the same complete position snapshot. A
captured security lifecycle leg or approved lifecycle event touching a selected
scope requires separate integration and stops this bounded route. Other lifecycle,
position and transfer/basis uncertainties cannot be promoted. Only wholly covered
`opening_history_missing` omissions may be replaced.

Every previously admitted parent allocation must remain identical. The output
retains all other omissions and adds only distinct supported allocations. Close
dates must fall inside the parent's existing report coverage; older supplemental
openings do not establish continuous older history, a complete boundary session,
lifetime completeness, current prices or a portfolio-wide performance total.

The output has its own calculation version and fingerprint and explicitly sets
financial acceptance and report-persistence authority to false. It is not a
`BoundedRealizedResult` or reporting authorization accepted by the current live
release writer. Making it a durable journal/report authority and publishing its
changed figures require compatible persistence plus fresh exact owner financial
acceptance; this approval does not include those live operations.

## Impact, validation and rollback

- Upstream: checksum-verified retained archive, private account binding and exact
  validated parent assembly/history.
- Changed component: separate recovered supplement and read-only preview in
  `src/onejournal/journal/recovered_opening_calculation.py`.
- Shared dependency: ordinary realized-item construction is factored without
  changing its legacy lineage, values or identity.
- Consumers: private human review only; no website, API or live writer route.
- Persisted state: private immutable artifacts and a disposable copy only. No
  migrations, canonical inserts, activations or report releases are required.
- Validation: focused equity/short-option cash and fee checks, exact source and
  identity failure cases, read-only replay, old calculation tests and actual-copy
  preservation of prior allocations and database bytes.
- Rollback: stop using the supplement/preview and revert the focused source
  change if needed. Original evidence, parent history and all earlier receipts
  remain intact; no live restoration or source deletion is needed.

This preserves the vision's evidence-before-interpretation and broker-independent
financial calculation principles. No strategic mapping, financial methodology,
operational acceptance or Phase 1 maturity claim is changed, so the strategic
anchors require no maturity update in this pass. Formal Phase 1 remains **8/12**.
